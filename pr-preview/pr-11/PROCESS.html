Workbench Agentic Development Process ​

This document describes the process I use for agentic development (“vibe coding”).

The process is intended to be generalizable to any modern agentic coding harness, including Claude Code, Codex, Copilot, Pi, and Oh My Pi. Throughout this document, the harness and the model driving it are collectively referred to as the agent.

The process starts with understanding the problem. For substantive changes, the agent grounds the domain, makes intent explicit with the human in a proposal, writes the approved change into the project's current specifications, then represents it independently in tests, documentation, and code. The resulting behavior is reviewed from multiple perspectives and finally verified by a human before release.

Goals ​

The Workbench process has several goals:

  • Preserve a coherent long-term vision for the project even as individual features are developed independently.
  • Make the intended behavior and scope of a feature explicit before implementation begins.
  • Give every current requirement one discoverable owner, so that nobody has to replay past proposals to learn what applies now.
  • Maintain multiple independently useful representations of that intent in current specifications, tests, guides, and code.
  • Make disagreements between those representations visible before a feature is released.
  • Use agents for implementation and review without making the agent the final authority over product intent.
  • Preserve enough design rationale, implementation history, and review discussion for future humans and agents to understand why the project is the way it is.
  • Keep dependent projects synchronized as new functionality moves from development previews to production releases.

Artifacts ​

The process produces and maintains ten kinds of artifact, described here as roles. The roles are conditional: one file can fill more than one, and a feature produces an artifact only for the roles it changes. Keeping Current Specifications gives authoring guidance and worked examples.

Work items, changesets and changelogs, review evidence, previews, and process machinery keep their own purposes. None of the roles requires separate narrative, use-case, flow, error-catalogue, view-model, toolchain, or architecture-overview documents.

Current specifications ​

Current specifications are the behavioral specifications and native contracts together: what the product must do at a given revision. Each normative fact has one current owner, in the representation that suits its surface. A library states its public surface in declarations and contract documentation covering defaults, errors, side effects, ordering, lifecycle, and compatibility. A protocol uses its native schema with semantic requirements beside it. An application workflow uses Gherkin or a current behavioral reference. One project may use all of these without choosing a project-wide mode, and an adequate existing source is reused rather than duplicated.

Contract text and type expectations are written or revised before implementation. Generated API reference publishes that source; it does not infer intended requirements from the implementation. A guide explains how to accomplish a task, while a reference states the contract on which that task depends.

A feature branch contains the proposed end state of the sources it changes. The main branch contains the integrated contract, and a release tag identifies the contract shipped with that release. The approved proposal bounds the authorized change; the branch's specifications state the resulting contract. Completed proposals never override current definitions. When current sources disagree, or elaborating them reveals a new substantive decision, the agent raises it with me.

Workbench supplies optional guidance for projects that specify a surface in Gherkin, in the specifying-behavior-with-gherkin skill and the .agents/templates/FEATURE.feature template. Nothing requires a project to use Gherkin, and Workbench adds no specification registry, identifier scheme, or coverage format.

In this repository, this document owns the process semantics. Record Validation and Workflow Status owns the contracts of mise run validate and mise run status. Source documentation and native tests own the specifics of the other tools.

Visions ​

A vision describes the project as a whole, including its purpose, minimum viable product target, design principles, and a possible future for the project beyond the current implementation.

The vision establishes the long-term direction against which individual proposals can be evaluated. It is created once near the beginning of the project and maintained as the project evolves.

Policies ​

A policy records a rule that should continue to be enforced across future work.

Policies capture constraints or conventions that should not have to be rediscovered from previous implementations or review discussions. A policy file always states the rule as it currently applies.

Decisions ​

A decision records an architectural or technical choice that should be remembered, including enough context to understand why that choice was made.

Future work may change a decision, but does so explicitly with me, by revising the decision's file or deleting it when it no longer applies.

Proposals ​

A proposal describes one change to the project: its motivation, scope, approach, and the delta it makes to the current specifications, policies, and decisions it affects.

Proposals describe what a feature does, not its look and feel. They link the current sources they change rather than maintaining a second complete contract. After implementation they remain part of the project's history, explaining why the project changed; they are not where its current requirements are read. A later proposal may supersede an earlier one that it replaces as a change, and that relationship is historical too.

Work items ​

A work item is a tracked unit of work in Beads: a task, a blocker, a discovered defect, or a durable memory the project needs to survive a context reset.

Work items answer a different question from proposals. The proposal records reviewed intent and is preserved as history; the Beads graph records what is ready, what is blocked, what was deliberately deferred, and what a future session must know. Neither substitutes for the other.

Tests, guides, and code ​

Tests verify the current specifications, implemented idiomatically for the language and environment: unit, integration, end-to-end, property, type, or other automated checks. Guides are human-consumable Markdown documentation explaining how to use the behavior the specifications define. Code is the implementation, including executable configuration.

Each is an independent interpretation of the same current requirements. A disagreement among them, or between one of them and the specification, reveals a defect in one of them or in the specification itself.

Previews ​

A preview is a prerelease form of the documentation or running software made privately available for human review.

A preview should be the cheapest realistic artifact through which a human can exercise the changed behavior. Both qualities matter: cheapest rules out standing up production-grade infrastructure merely to review a change, and realistic rules out screenshots, transcripts, and descriptions of what would happen.

What that artifact is depends on what the project is:

A project wires the mechanism matching its own shape. Previews are private by default; a project makes one public only deliberately, as when a library publishes its documentation.

Project Vision ​

A new project begins with the creation of its vision document.

The agent and I develop the vision together before normal feature work begins. The document describes both the minimum viable version of the project and the broader direction in which the project may evolve.

The vision is not a collection of committed feature specifications. Individual changes are designed through proposals, and the project's requirements live in its current specifications.

Unlike proposals, however, the vision is a living document. After accepted features materially alter the project's capabilities or direction, the vision is updated so that it continues to describe the project accurately.

Feature Development ​

Substantial feature work proceeds through five phases:

  1. preparation,
  2. proposal development,
  3. implementation,
  4. human review, and
  5. completion and release.

The process is iterative. Findings during implementation or review may cause the proposal itself to change, at which point the implementation is reevaluated against the revised proposal.

The full feature loop applies to changes that decide new behavior or resolve a meaningful design choice. A correction whose intent is already established, such as an unambiguous bug fix or dead link, may be handled directly: it implements the current requirement. Polishing an interface's look and feel is handled directly too, as described under Look and feel. If investigation shows the behavior was never specified and needs a decision, or uncovers another design choice, return to proposal development before implementing it.

The primary agent owns domain understanding, conceptual modeling, and proposal intent, and it usually implements the work itself. It delegates only independent slices that can run in parallel, and it uses a reframer when the problem formulation no longer explains the evidence. An independent adversary tries to falsify the finished work and reports findings without editing it.

Before entering the proposal path for a change, the agent asks the human whether they want a proposal, even if the request sounds like a feature or asks for one. Look-and-feel polish never enters that path, so it needs no question. An explicit yes for this change authorizes its proposal and later revisions, not future proposals. A no rules out the proposal and its draft pull request: proceed directly when intent is already clear, or clarify and narrow the work before implementation when a consequential design choice remains. This question precedes branch creation and PR preparation so unnecessary draft PRs are not opened.

Look and feel ​

A proposal, and the current specifications it changes, say what a feature does: what a user can do, what they can find out, the states and outcomes they observe, the errors they are told about, and any guarantee the project makes about their data, privacy, accessibility, or platform requirements I have chosen. Its look and feel is how the interface looks and how it is operated: layout, sizes, spacing, typography, color, iconography, motion, grouping and placement, which control presents a choice, what activating an element opens, and the wording of labels and messages. I decide look and feel by looking at the running UI, not by approving prose, so it is never recorded in a proposal or a current specification, and changing it never needs one.

Two cases sit close to the line. What a message must convey is what the feature does; its words are look and feel unless the exact words are themselves a requirement, such as legal text, text a user must type or match, or a term the project's vocabulary fixes. An accessibility commitment is what the feature does; how a screen meets it is look and feel, and polish never breaks the commitment. The same line holds for a command-line or terminal interface: its colors, alignment, progress display, and help-text wording are look and feel, while its commands, flags, exit codes, and machine-readable output are what it does, as is a library's API.

The test is whether a sentence would need to change if the screen were redesigned while the feature did the same thing. When a change could be either, the agent asks me which in one line before acting. A change that removes something a user could do or find out is what the feature does. A look-and-feel detail an earlier proposal happens to pin, such as a window width, is still look and feel: polish may change it, and the proposal stays as the history of what was decided then.

Polish is the work of refining look and feel with me on the running UI, and the polishing-a-ui skill describes it. During implementation, the agent chooses the look and feel a proposal leaves open to fit the project's existing interface and its platform's conventions. During human review, look-and-feel feedback is applied while the proposal stays active-review. Between proposals, polish needs no proposal question: the agent makes the changes I direct and lands them the way the project lands other changes made without a proposal. A request that would change what the feature does stops polish and takes the proposal path. A look-and-feel convention I keep applying may become a policy after we discuss it.

Agent orchestration ​

The project's Oh My Pi workflow tool under .omp/tools/dynamic-workflows/ is for a dependency graph of agent work: independent branches that feed a later synthesis, or result-driven branches and pipelines. A single small task stays inline; a fixed batch of independent slices uses ordinary task delegation. Workflow scripts orchestrate subagents deterministically and expose phases, but the agents still need bounded ownership and the strategist still owns intent and review. A failed branch yields null; treat it as a missing result, not evidence of success.

Preparation ​

After the human opts into a proposal for this change, work on the feature begins in an isolated Git branch.

The agent creates the branch, pushes it to the project's origin remote, and creates a draft pull request for the work.

The pull request becomes the durable workspace for the feature. It collects the proposal, implementation, review discussion, agent status reports, and other artifacts associated with the change.

The pull request stays draft while it contains only the proposal. Once the complete implementation has passed its applicable checks and reached the pushed feature branch, and continuous integration has passed on that revision, mark the pull request ready for maintainer review. No git hook runs the full gate; continuous integration runs it on every push, so the agent waits for it rather than assuming a local run covers the pushed revision. Keep agent reviews, the preview, and the readiness report on that PR while the maintainer can inspect and comment on the implementation.

Proposal Development ​

Before implementation, the agent and I write a proposal describing the change.

The proposal identifies the current specifications, policies, and decisions the change affects, links them, and explains the delta to each, along with scope, alternatives, approach, and compatibility work. It names any necessary information that has no current home. It should make the change concrete enough that the agent can revise those sources and then derive tests, documentation, and an implementation without relying primarily on the original conversational request. Requirements the change leaves alone are linked, not restated.

We iterate on the proposal until I am satisfied that it represents the change I intend to make.

The proposal is preserved after the feature ships. It becomes part of the historical explanation of the change rather than merely temporary planning material. Later work changes the current sources directly and explains itself in its own proposal.

Ground the problem ​

When a change depends on domain knowledge that cannot safely be inferred from the request, the strategist uses grounding-a-problem before selecting an approach. Prefer authoritative sources; distinguish established knowledge, observed repository behavior, inference, and untested hypotheses. Record the context needed to judge the proposal in Domain grounding. When no independent research is needed, say why in that section rather than manufacturing it.

When important domain concepts, identities, relationships, states, or vocabulary change, use ontology-review before those assumptions harden into the detailed design. A material conceptual conflict goes back to grounding or the proposal, not directly into code.

Study the existing baseline ​

After grounding, inspect the closest implementation, prototype, workflow, or prior attempt. Record what works, what should be preserved, and what is incidental or compromised in Existing baseline. Existing code is evidence of current behavior, not authority about the domain.

Decide and record intent ​

Compare viable approaches against the grounded constraints, vision, current specifications, policies, and decisions. Write the selected change in the proposal's Detailed design as a delta to the current sources it names, with scope and unresolved questions explicit. The human decides when the proposal is settled and sets awaiting-implementation; an agent must not approve its own proposal.

Implementation ​

After the human sets awaiting-implementation, the agent implements the proposal itself unless independent slices can run in parallel; a delegated slice gets the current sources it touches, its detailed design, constraints, scope, and verification commands. Use reframing-a-problem when repeated local fixes no longer explain the problem, or when a slice reports that the evidence contradicts the proposal's model; revise intent with the human before continuing.

Specification Updates ​

The agent first revises the affected current specifications, and any policy or decision agreed in the proposal, so they state the approved end state. It reuses each source's existing representation, or adds the smallest adequate source for a requirement that has no home. A new substantive decision discovered while elaborating them goes to me. The agent cannot approve a requirement by documenting whatever an implementation happens to do.

Behavioral Tests ​

The agent then writes failing tests for the observable behavior the revised specifications require, when such tests add meaningful protection, and watches them fail.

These tests establish an executable interpretation of the specification before the implementation itself can influence what is considered correct. Existing native tests that still apply are kept. A test that only confirms a document exists, or that a test carries an identifier, establishes nothing about behavior.

The goal is not merely to increase test coverage, but to encode the externally meaningful behavior of the feature.

Usage Guides ​

When the change has a user-facing surface, the agent then writes or revises its guide from the intended contract before production code exists, linking the current sources it explains. This forces the intended interface to be explainable independently from the implementation.

The agent compares the guide with the tests before implementing. A change with no user-facing surface needs no invented guide.

Implementation ​

The agent implements the feature against the current specifications, tests, and guides.

Implementation continues until the project's quality gates pass. Depending on the project, these may include:

  • formatting,
  • linting,
  • type checking,
  • building,
  • unit tests,
  • integration tests,
  • end-to-end tests, and
  • other project-specific validation.

Passing the quality gates is necessary but not sufficient for the feature to be considered complete.

Self-Check ​

Once the implementation passes its automated checks, the agent reads the proposal's authorized change, the affected current specifications, tests, guides, and code together to find disagreement between the representations: tests that miss specified behavior, guides that describe something the tests do not exercise, code that implements behavior the specifications do not describe, specifications that go beyond what the proposal authorized, or details that quietly changed scope or intent. Look and feel the proposal leaves open is not such a disagreement, and neither is a look-and-feel detail the proposal pinned that I have since changed through polish. It also asks whether this is the implementation that should remain — whether its structure expresses the specified model or leaks implementation conveniences into public behavior. It fixes what it finds, or records a deliberate divergence for the human.

Adversarial Review ​

The implementation is then reviewed once, independently, by a subagent with fresh context and preferably a different model. It receives the proposal, the current specifications and relevant unchanged constraints, and the work, and tries to falsify the claim that the work is done: missing or wrong behavior, weak or misleading tests, regressions, and security risks. It ignores style and look and feel, and reports without editing.

The primary agent fixes confirmed defects inside the proposal's scope. A finding outside that scope is never a reason to widen the change: it is declined with reasoning or filed in Beads. Declined findings are preserved for human review rather than silently discarded. The adversarial reviewer does not decide whether the feature is acceptable.

Preview ​

Produce the preview selected in the proposal after review findings are resolved. It must be a usable build, installation, or deployed surface through which the human can exercise the changed behavior. Confirm that it runs; a green preview build alone is insufficient. A pure refactor without an exercisable surface needs no fabricated preview.

Readiness Report ​

After the self-check, the adversarial review, and the preview, the agent posts a readiness report describing implemented behavior, the evidence its verification produced and that evidence's limits, any declined findings, and how to exercise the preview. reviewing-an-implementation owns this handoff. Move the proposal to active-review with that report; the pull request should already be ready from the complete, verified implementation. If it remains draft, verify that implementation is in its pushed revision and correct the PR state before posting the report.

Human Review ​

Human review determines whether the implementation actually satisfies the intended feature.

I review both the agent's readiness report and the artifacts produced during development. Depending on the feature, this may include:

  • the code diff;
  • the proposal;
  • the revised current specifications;
  • tests;
  • rendered preview documentation;
  • a preview application deployment; and
  • a preview package consumed by draft pull requests in dependent projects.

Review is not limited to reading generated artifacts. The preview forms of the feature are intended to make the actual behavior directly inspectable whenever possible.

I leave general or inline pull request comments describing changes I want the agent to make. I may also edit and commit prose or code directly during review.

I then instruct the agent to process the review feedback. Additional context may be supplied directly to the agent when it does not belong in a pull request comment.

If the feedback changes what the feature does, or a design decision the proposal records, rather than merely correcting its implementation, the agent updates the proposal first, then the affected current specifications.

Feedback on look and feel alone is applied while the work stays in review: the agent changes the code, runs the quality gates, pushes, and refreshes the preview, without editing the proposal, changing its status, posting another readiness report, or repeating the adversarial review. Feedback that mixes both is split, and only the part that changes what the feature does or a recorded design decision goes back through the proposal.

The agent then repeats the affected specifications, tests, guides, code, validation, self-check, and adversarial review against the revised proposal as necessary.

Implementation and human review therefore form a loop:

proposal → current specifications → tests → guides → code → validation → self-check → adversarial review → preview → human review → revision

The loop continues until I accept the feature.

Policies and Decisions ​

Feature development may reveal knowledge that should outlive the proposal itself.

When agreed work establishes, changes, or retires a rule that future work should continue to enforce, the agent records it as a policy after discussion with me: it adds a policy, revises the existing one, or deletes it when the rule no longer applies. An architectural choice that future work needs to understand is handled the same way as a decision. A proposed policy or decision stays on the change branch until we agree it.

A revised record keeps its file and identifier, and the same change updates every current reference to it. A retired record's file is deleted and its identifier is not reused. When deleting it would break a historical link that should keep working, that link points to an immutable Git revision instead. Git history and the proposal that made the change preserve the earlier version and its reasons. A constraint that still binds a supported compatibility promise or an unfinished migration remains in force until that obligation ends.

Policies and decisions are not substitutes for proposals or current specifications. A proposal explains a particular change; a policy or decision holds a continuing constraint or choice; a product guarantee stays with the specification that owns it. Development instructions for agents stay in .agents/.

Future proposals should be evaluated against the current vision, specifications, policies, and decisions.

Work Tracking ​

During proposal development, implementation, automated validation, adversarial review, or human review, the agent discovers work that should be preserved independently of the current pull request. Beads (bd) holds it, along with the project's durable memory. My own planning lives in GitHub Issues and Projects; Beads does not replace them, and agents leave them to me.

A defect that prevents the current implementation from satisfying its proposal remains part of the current work and should be fixed before the pull request is accepted. The agent does not file a work item merely to defer work the proposal already requires.

A defect is recorded in Beads instead when it is outside the scope of the current proposal, already exists on the main branch, affects another feature or project, or otherwise represents legitimate future work that should survive beyond the current pull request.

Before creating a new item, the agent searches the existing graph — bd ready for what is startable, then bd search and bd list across every state, open through closed, with the result limit lifted — so the same defect is not filed twice.

A work item should contain enough information for a future human or agent to understand and reproduce the defect without depending on the conversational context in which it was discovered: a concise description of the incorrect behavior, the behavior expected instead, reproduction steps or a minimal reproduction, relevant environment or version information, links to the proposal, pull request, test, or code where it was discovered, and any known constraints, suspected causes, or related defects.

sh
bd create "Parser rejects nested optional routes" \
  --type=bug --priority=1 \
  --description="Expected: ($lang).($region).products.tsx produces two nested optional segments. Actual: route discovery fails with an invalid segment error. Repro: create that file and run route discovery. Found under proposal.0007 in PR #42; out of scope because that proposal does not change optional-route parsing."

The agent applies the project's existing types, priorities, labels, and dependency relationships when those conventions exist. Dependencies matter: an item blocked by another is linked so bd ready stays honest about what can actually be started.

When a newly discovered defect is relevant to the current pull request but intentionally outside its scope, the agent links the work item from the pull request or an appropriate review comment. This makes the decision to defer the defect explicit and leaves a durable path from the context in which it was discovered to the future work needed to resolve it.

If subsequent work fixes the defect incidentally, the agent closes the item with a reference to the pull request or commit that resolved it rather than leaving it stale.

Durable project knowledge — a constraint learned the hard way, a decision too small for a record but too costly to rediscover — goes in bd remember, not a memory file.

Beads across machines ​

Agents work on the same project from several machines. Each machine keeps its own Beads replica of the project: a full local database, shared by every worktree of that machine's checkout, that works offline. The replicas meet at a remote, refs/dolt/data on the project's own GitHub repository. It is not a branch, and syncing never creates or updates one.

A replica sees another machine's work only after a sync, which pulls from the remote, stops on any conflict Beads cannot settle by itself, and pushes. Syncs happen at points the process already has: when the agent orients itself with mise run status, when git push and git pull run, after the agent changes Beads items another machine should see, and around every claim. A claim is atomic only within one replica, so each machine claims under its own identity and checks after syncing that its claim survived. The agent resolves a sync conflict itself and reports afterwards what it resolved and why. The tracking-work skill holds the procedure.

Completion ​

Once the feature has passed human review, the agent completes the authorized integration and delivery work.

Records ​

The agent finalizes the policies and decisions the change agreed, giving each its current status, and confirms that the current specifications on the branch state what I accepted.

Vision Update ​

The agent reviews the project vision and updates it when the completed feature changes the project's current capabilities, minimum viable product, or broader direction.

Because the vision is intended to describe the project as it currently exists and where it is heading, accepted work should not leave it stale.

The agent may consult me before making substantial changes to the vision.

Changeset ​

Every pull request carries a changeset. mise run changeset writes one into .changeset/, naming the bump and describing the change for the changelog a user will read — not for the reviewer who already saw the diff. A change with no user-visible effect still carries a changeset, created with --empty. CI rejects a pull request without one; the release pull request is exempt.

Implementation Record ​

After acceptance, the records, and the vision update, set the proposal to implemented in the feature pull request before merging it. This records the approved implementation, not integration or release. Keep acceptance and outstanding delivery visible in the proposal or pull request. Verify the updated integration candidate; do not open a follow-up pull request solely to change the proposal status.

Confirm the status record is in the pull request revision, not only the local checkout, before merging. If an earlier pull request has already merged, inspect its merged revision before concluding a local accepted status means the record is missing. Report an absent record to the human for reconciliation rather than treating a merged pull request as editable or opening a status-only pull request.

Merge ​

The agent merges the accepted pull request into the project's main branch after confirming that the implementation record is in its latest revision and continuous integration has passed on that revision. If the pull request remains draft, treat that as an anomalous state: verify its pushed implementation, mark it ready, and verify the updated revision before merging. The merge lands the revised current specifications together with the implementation that realizes them.

The merge should preserve enough information for future humans or agents to recover:

  • what was proposed;
  • what was implemented;
  • why important decisions were made;
  • what problems were discovered during review;
  • what changes were requested; and
  • how the final implementation differs from earlier revisions.

The proposal and relevant pull request history therefore form part of the long-term knowledge base of the project rather than disposable development scaffolding.

Release ​

When a release is required and the human has explicitly authorized it, release through the project's CI/CD process using the required mechanism. Merge approval alone does not authorize publication. implemented records accepted implementation in the feature pull request, not a completed release. Track any required release separately until performed; merge-only delivery needs no fabricated release.

Dependent Work ​

If other projects contain draft pull requests depending on a preview version of the feature, the agent updates those pull requests to consume the production release.

Once their dependency on unreleased work has been removed, the agent marks those dependent pull requests as ready for review when appropriate.

This allows work across multiple repositories to be developed against previews without leaving those preview dependencies in place after release.

Cleanup ​

After required delivery, the agent cleans up temporary files, preview configuration, and stale feature branches only with the relevant authorization.

Branch deletion and published-artifact teardown require explicit human confirmation. Cleanup is a separate operation, not an automatic result of merging or setting implemented.

Process Summary ​

At the project level:

vision → feature proposals → current specifications and implemented project → updated vision

For each feature:

human opts into proposal → branch → draft pull request → grounding and ontology review when needed → baseline study → proposal → current specifications → tests → guides → code → validation → ready pull request → self-check → adversarial review → preview → readiness report and active-review proposal → human review → revision or acceptance → records and vision update → implemented record in the feature pull request → merge → required release → dependent updates → authorized cleanup

The central invariant of the process is that no single artifact defines the feature by itself.

The proposal records the change and its reasons. Current specifications state what is required now. Tests encode that behavior. Guides explain it. Code implements it. Previews expose it for direct inspection. Independent agent review attempts to find contradictions and defects. Human review determines whether the result is actually the feature that was intended.

Each representation acts as a check on the others.
