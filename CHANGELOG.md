# Changelog
## 3.0.1 (2026-11-17)

### Fixes

#### Check pull requests from a fork's release branch

The `.github/workflows/workbench.yml` that `workbench project init` generates skipped the commit and change-file checks for any pull request whose branch was named `release`, including one from a fork. It now skips them only for a `release` branch in the same repository, where Knope opens its release pull request. A project that already has the file should change the job's `if:` to `github.head_ref != 'release' || github.event.pull_request.head.repo.full_name != github.repository`.

## 3.0.0 (2026-11-16)

### Breaking Changes

#### Depend on Workbench instead of copying it

Workbench is now a versioned package rather than a template to copy. Each release ships the `workbench` CLI and the plugin content harnesses load — the process contract, skills, rules, templates, and the Hugo theme for the record site — as one archive per platform. A project pins a release in `mise.toml` (`mise use github:markmals/workbench@3`), and `mise install` links it at the gitignored `.workbench`. Committed declarations in `.claude/settings.json` and `.omp/config.yml` load it in Claude Code and Oh My Pi; a release reaches a project as a one-line change to the pin.

The TypeScript tools are replaced by `workbench` commands, which print JSON with structured errors by default and `--output text` for people: `workbench workflow status`, `workbench records validate`, `workbench project validate`, `workbench commits check` and `scopes`, `workbench change-files create` and `check`, and `workbench beads sync`, `claim`, and `close`. Discover them with `workbench cli search`, `workbench schema`, and `workbench docs search`. The `status`, `validate`, `beads:sync`, `beads:claim`, and `beads:close` tasks keep their names; `mise run beads:close` now takes `--reason "<text>"`. A Beads sync that cannot reach the remote never stops a claim or close, and every report of it names the cause with the same error code `workbench beads sync` uses. `workbench project init` sets Workbench up in a repository and never overwrites a file, and `workbench project validate` reports a project skill or rule that reuses a Workbench name, a `.workbench` link that disagrees with the pin, missing harness declarations, and vendored Workbench files. The four rules now carry frontmatter, so Oh My Pi lists them.

Workbench requires no Node, TypeScript, or Oh My Pi packages. Knope replaces Changesets: every pull request adds a Knope change file (`workbench change-files create`), which opens with a summary heading after its frontmatter, or carries a `Release-Note: none` commit trailer, and merging Knope's release pull request publishes a release. Hugo with Pagefind replaces VitePress, dprint replaces Oxfmt in Workbench itself, Varlock replaces Fnox, and the Oh My Pi `workflow` tool is gone in favor of each harness's own delegation.

Adopting this release replaces the copied files the earlier entries in this changelog asked you to merge. Follow [Adopting Workbench](https://markmals.github.io/workbench/guides/adopting-workbench/): pin the release and run `workbench project init --dry-run`, then `workbench project init`; move your additions out of shared files into project rules, skills, or template overrides; delete the vendored copies its receipt lists; convert pending Changesets entries to change files and move your release flow to Knope; move a published site to Hugo; replace Fnox with Varlock; and run `mise run check`.

### Features

#### Drop harness hooks and sync Beads across machines

Agent sessions no longer pay for work they did not ask for. The three Oh My Pi extensions are gone: nothing formats after every edit, runs `mise run check` before every stop, or injects `bd prime` into the first turn. The `pre-commit` hook still formats staged files, the agent still runs `mise run check` before claiming work is done, and the `pre-push` hook no longer runs the gate. CI runs it on every push, and agents wait for CI to pass before marking a pull request ready or merging it.

Beads now stays current across machines. `mise run status` syncs this machine's Beads replica with `refs/dolt/data` on the project's own repository, then shows the sync outcome, ready work, the items in progress and who holds them, and the project's memories; `--json` adds a `beads` object. `git push`, `git pull`, and rebases sync through hk, and `mise run beads:sync` syncs on demand. `mise run beads:claim -- <id>` claims an item as `<user>@<short host>` and reports whether the claim survived the sync (`claimed`, `claimed-unpublished`, `held`, or `lost`); `mise run beads:close -- <id> "<reason>"` closes it as the same claimant and syncs. No sync creates a Git branch, so GitHub shows no "recently pushed" banner, and no sync runs against a Beads remote that is not the project's own `origin`. The `tracking-work` skill explains replicas, claims, and how to settle a sync conflict. `mise run setup` restores an existing project's replica with `bd bootstrap` instead of creating an unrelated database. GitHub Issues and Projects hold the owner's planning; Beads holds the work agents discover and the project's memory.

What adopters have to do: delete `.omp/extensions/` and `tools/format-after-edit.test.ts`; copy `tools/bd.ts`, `tools/beads.ts`, `tools/beads-claims.ts`, `tools/beads-cli.ts`, `tools/beads-remote.ts`, `tools/beads-report.ts`, `tools/fake-bd.ts`, `tools/beads.test.ts`, and `.agents/skills/tracking-work/recovering-a-sync.md`; and merge the changes to `mise.toml` (the `DOLT_REMOTE_INFO_BRANCH` entry, the `beads:sync`, `beads:claim`, and `beads:close` tasks, and `setup`), `hk.pkl` (the `pre-push`, `post-merge`, and `post-rewrite` steps, and no `pre-push` check), `.beads/config.yaml` (`dolt.auto-push: false`), `tools/status.ts`, `tools/status.collection.test.ts`, `tsconfig.json`, `AGENTS.md`, `PROCESS.md`, `README.md`, the `tracking-work`, `writing-a-proposal`, `implementing-a-proposal`, `reviewing-an-implementation`, and `completing-a-feature` skills, the enforcement hierarchy, `.github/workflows/ci.yml`, and the `adapting-your-harness`, `getting-started`, `record-validation`, and `running-a-feature` guides. A project whose `.beads/` came from the Workbench template replaces it as the getting-started guide describes; until then, its syncs fail rather than reach Workbench's repository. A project that set `dolt.auto-push: true` turns it off, and one whose repository has a `__dolt_remote_info__` branch deletes it once. Then run `mise run setup` on every machine. Claims made before this change hold a Git user name; move your own to `<user>@<short host>` as the `tracking-work` skill describes.

#### Keep current requirements in the sources that own them

Maintain current requirements in API contracts, reference documentation, or Gherkin as appropriate to each surface. Proposals now explain changes to those sources. Workbench includes reusable optional Gherkin authoring guidance, examples, and a feature template without requiring a new runner or specification registry.

Policies and decisions can be revised in place or retired. When adopting this version, remove their `supersedes` metadata and consolidate any still-applicable requirements before deleting old records. `established-by` is optional historical provenance. Replace guide `describes` metadata with ordinary links to current sources, and update the validator, record templates, process skills, and guides together. Historical proposal relationships and native test suites remain supported.

#### Leave look and feel to the running UI

Proposals now say what a feature does and leave its look and feel — layout, sizes, spacing, type, color, motion, which control presents a choice, how it is operated, and wording — to the human on the running UI. Look-and-feel feedback during human review is applied while the proposal stays `active-review`, with no proposal edit, status change, readiness report, or second adversarial review. Polishing an interface between proposals needs no proposal question; the new `polishing-a-ui` skill describes the loop and stops when a request would change what the feature does.

What adopters have to do: copy `.agents/skills/polishing-a-ui/`, and merge the changes to `AGENTS.md` ("Does this change need a proposal?" and "Stay inside the proposal"), `PROCESS.md` (the new Look and feel section, the self-check, and Human Review), `README.md`, the `writing-a-proposal`, `implementing-a-proposal`, `reviewing-an-implementation`, and `adversarial-review` skills, the proposal and pull-request templates, the status messages in `tools/status.ts`, and the `running-a-feature` and `writing-a-good-proposal` guides. Existing proposals need no edits; look-and-feel details already written into one stand as decided at the time and may be refined through polish without revising it.

#### Replace the Vite+ toolchain with mise, hk, and Beads

Replace the Vite+ toolchain with the platform-neutral tooling layer the project templates share: mise owns every pinned tool and every task, hk owns every git hook, Fnox owns secrets, Beads owns the work graph, Changesets owns the changelog, and Worktrunk owns worktrees.

What adopters have to do: install mise, then run `mise install` and `mise run setup` instead of `vp install`. In an existing checkout, first run `git config --unset core.hooksPath`: hk registers its hooks through git's `hook.<name>.command` config, and a leftover `core.hooksPath` from `vp config` keeps the old Vite+ hooks running beside them, so commits fail. Every command changes name — `mise run check` is the gate, `mise run status` reports the phase, `mise run fmt` formats. Formatting, lint and type checking now come from `.oxfmtrc.jsonc`, `.oxlintrc.jsonc` and `tsrs` rather than `vite.config.ts`, which is gone along with `.agents/hooks/`; the `commit-msg` hook reads its scopes from the new `.agents/commit-scopes`. Deferred defects go to Beads instead of GitHub issues, and the `tracking-defects` skill is now `tracking-work`. Every pull request carries a changeset.
